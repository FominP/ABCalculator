# Обработка данных и телеметрия

Статус решения: **телеметрия отсутствует**. На 27 ноября 2026 года приложение не
подключает продуктовую аналитику, рекламные трекеры, session replay или внешний
сервис сбора ошибок. Это решение распространяется на браузер и Flask-приложение;
операционные данные, которые необходимы Render для работы хостинга, описаны ниже.

## Как проходит запрос

1. Пользователь вводит агрегированные параметры эксперимента в браузере.
2. `static/script.js` собирает значения полей и отправляет по HTTPS запрос
   `POST /calculate` с заголовком `Content-Type: application/json`.
3. JSON содержит `test_type` и объект `params`. Браузер передаёт значения полей
   строками; Flask преобразует их в числа и проверяет допустимые диапазоны.
4. Flask выполняет расчёт в процессе Render с помощью `ab_test_analyzer` и
   возвращает JSON с результатом или ошибкой валидации.
5. Браузер показывает ответ в DOM и, где применимо, строит график. Приложение не
   записывает запрос или ответ в cookies, `localStorage`, `sessionStorage`, базу
   данных или файл. Результат попадает в буфер обмена только после явного нажатия
   пользователем кнопки «Копировать».

Таким образом, экспериментальные параметры покидают браузер и достигают Flask и
инфраструктуры Render. Они не отправляются другим поставщикам приложением.

При открытии страницы браузер отдельно загружает Bootstrap и Chart.js с
`cdn.jsdelivr.net`. CDN получает обычные сетевые метаданные загрузки ресурса
(включая IP-адрес, User-Agent и Referer), но параметры формы и результаты в эти
запросы не включаются. Ссылка на GitHub не создаёт запрос к GitHub, пока
пользователь сам по ней не перейдёт. jsDelivr используется для доставки статических
библиотек, а не для аналитики; при следующем пересмотре зависимостей стоит оценить
локальное размещение этих файлов, чтобы убрать лишнего сетевого посредника.

## Что отправляется в `/calculate`

Общая форма запроса:

```json
{
  "test_type": "z_proportions",
  "params": {
    "conv_control": "200",
    "n_control": "1000",
    "conv_test": "250",
    "n_test": "1000"
  }
}
```

Состав `params` зависит от анализа:

| `test_type` | Поля |
| --- | --- |
| `z_proportions` | `conv_control`, `n_control`, `conv_test`, `n_test` |
| `t_means` | `mean_control`, `std_control`, `n_control`, `mean_test`, `std_test`, `n_test` |
| `chi_square` | `conv_control`, `nonconv_control`, `conv_test`, `nonconv_test` |
| `srm` | `n_control`, `n_test`, необязательное `expected_ratio` |
| `mde` | `baseline_conversion`, `n_control`, необязательные `n_test`, `alpha`, `power` |

Это агрегированные данные эксперимента: количества, размеры выборок, средние,
стандартные отклонения, доли, уровень значимости и мощность. Идентификаторы
пользователей, строки исходных событий и персональные данные контрактом не
предусмотрены и не должны вводиться в поля формы.

Ответ может содержать статистику теста, p-value, доверительный интервал,
заключение, интерпретацию, данные графика, MDE или параметры SRM. Ответ возвращается
тому же клиенту и не сохраняется приложением.

## Логирование и хранение

В `app.py` нет логирования тела запроса, `params`, результата расчёта или текста
ответа. Приложение не настраивает файловые логи и не пишет эти данные в
`stdout`/`stderr`. Регрессионный тест `tests/test_privacy.py` отправляет уникальные
маркеры как вход и результат и проверяет, что они отсутствуют в Python logs,
`stdout` и `stderr`.

Gunicorn и Render всё равно формируют операционную границу вокруг приложения:

- Render захватывает вывод процессов в `stdout` и `stderr`; поэтому будущий код
  также не должен печатать payload, результат или исключение вместе с данными.
- В HTTP request logs, доступных на поддерживаемых тарифах, Render документирует
  метод, статус, запрошенный URL, время ответа и идентификатор запроса. Тела
  запросов не входят в документированный формат request log. Параметры
  эксперимента нельзя добавлять в URL или query string.
- `render.yaml` размещает сервис в регионе `frankfurt` на бесплатном тарифе.
  Render указывает, что логи хранятся в регионе сервиса. Для workspace Hobby
  документированный срок доступности логов — 7 дней; срок зависит от тарифа.
- На инфраструктурном уровне Render получает IP-адрес, сведения об устройстве и
  браузере, время запроса, сетевые заголовки и другую операционную информацию.
  Политика Render также описывает определение геолокации по IP. Приложение не
  копирует эти данные в собственное хранилище и не связывает их с параметрами
  эксперимента.

Источники: [Render: Logs in the Dashboard](https://render.com/docs/logging),
[Render: Privacy Policy](https://render.com/privacy) и
[Render: logging and observability](https://render.com/articles/how-render-handles-logging-and-observability).
Фактические production logs следует периодически проверять в Render Dashboard;
операционная проверка доступа к dashboard отслеживается отдельно в issue #10.

## Данные, которые запрещено сохранять и отправлять

Следующие данные нельзя записывать в application logs, сохранять в базе/файлах,
добавлять в URL, breadcrumbs, traces, session replay, аналитику или отчёты об
ошибках:

- полное тело запроса и объект `params`;
- количества конверсий и неконверсий, размеры выборок и SRM counts;
- средние, стандартные отклонения, baseline/rates, `alpha`, power и expected ratio;
- статистика теста, p-value, доверительные интервалы, MDE, выводы и данные графика;
- любые идентификаторы эксперимента, компании или пользователя;
- IP-адреса, точная геолокация, email и другие персональные или чувствительные
  данные, если такой код когда-либо появится в приложении.

Допустимы только минимальные операционные сведения, не содержащие перечисленных
значений: версия приложения, имя маршрута (без query string), класс ошибки,
HTTP-статус и длительность. Даже этот набор нельзя отправлять внешнему поставщику,
пока отдельное решение не одобрит конкретную схему событий.

## Почему сейчас нет телеметрии

Преимущества решения:

- нет дополнительного получателя данных и клиентского трекера;
- меньше риск случайно передать статистику эксперимента через event properties,
  exception locals, breadcrumbs или session replay;
- нет cookies/идентификаторов аналитики, consent-платформы и vendor lock-in;
- меньше зависимостей, сетевых запросов и эксплуатационной нагрузки.

Стоимость решения:

- неизвестны посещаемость, популярность методов и воронка использования;
- ошибки приходится воспроизводить по сообщению пользователя и проверять по
  минимальным логам Render;
- сложнее заметить редкие клиентские ошибки и оценить влияние релиза.

Для текущего небольшого калькулятора снижение риска важнее этих сигналов.

## Рассмотренные альтернативы

Ни одна альтернатива сейчас не одобрена и не подключена.

| Вариант | Приватность и ограничения | Решение |
| --- | --- | --- |
| Агрегированные счётчики внутри сервиса | Можно считать только вызовы маршрутов и классы статуса без payload, но для долговременных метрик потребуется новое хранилище, срок удаления и защита от связывания с IP. | Не внедрять: у бесплатного stateless-сервиса нет подходящего хранилища, а продуктовая ценность пока не оправдывает его. |
| Plausible Analytics | Не использует cookies или постоянные идентификаторы посетителя; IP и User-Agent обрабатываются с ежедневно меняющейся солью, а исходный IP не сохраняется. Данные посетителей размещаются в ЕС. Hosted-версия предлагает 30-дневный trial, но не постоянный бесплатный тариф; статистика хранится, пока активен аккаунт, и удаляется по запросу владельца. | Наиболее приемлемый вариант для будущих агрегированных page views, но сейчас не подключать: это новый обработчик данных и платная зависимость. См. [security](https://plausible.io/security) и [plans](https://plausible.io/docs/subscription-plans). |
| Sentry для server-side ошибок | Может дать stack trace и группировку ошибок, но exception locals, request context, breadcrumbs и IP способны раскрыть запрещённые данные. Доступны US и EU (Германия) data regions, в том числе для бесплатного Developer plan; квоты и retention надо повторно проверить перед выбором. | Не подключать без строгого allowlist/scrubbing, отключения IP, request bodies, locals, breadcrumbs, tracing и replay, а также проверки региона и срока хранения. |

Самостоятельно размещённая аналитика не устраняет необходимость определить
правовое основание, доступ, срок хранения, резервные копии и процедуру удаления;
она только меняет поставщика инфраструктуры.

## Правило для будущих изменений

Переход из состояния «телеметрия отсутствует» в «опциональна» или «включена»
требует отдельного issue и явного одобрения до добавления SDK или скрипта. В issue
нужно зафиксировать:

1. поставщика, цель и полный список event names и разрешённых полей;
2. cookies/local storage, обработку и усечение IP;
3. срок хранения, удаление, data residency и subprocessors;
4. лимиты бесплатного тарифа и поведение после их исчерпания;
5. необходимость consent/opt-out;
6. сетевой тест, доказывающий отсутствие всех запрещённых значений в payload.

Независимо от будущего решения количества, rates, means, standard deviations,
request bodies и calculation results никогда не могут быть полями телеметрии.
Одобрение поставщика должно создать отдельную implementation-задачу; пока такого
одобрения нет, отдельная задача не создаётся.
